# Empirical Prompt Tuning

独立した実行者が生成した成果物を評価し、観測された問題に対応する最小修正を行う。通常のスキル編集だけを理由に実験を開始しない。

## 評価を設計する

description の発動条件と本文の範囲を照合し、評価対象を確定する。実際の使用場面と失敗しやすい境界を含むシナリオ、成果物の要件、試行・時間の上限を実行前に決める。重要要件には `[critical]` を付け、採点基準を途中で変更しない。

各条件には同じ入力と実行環境を使う。実サービスへの書き込みや費用が生じる評価は、その操作が依頼で許可されているか確認し、可能なら隔離 fixture で評価する。

## 実行・修正

新規 subagent に対象指示、現実的な依頼、必要な生の資料、使用可能な環境を渡して実行させる。意図した回答や修正仮説は渡さない。依頼例・報告項目が必要なら [実行者への依頼](references/executor.md) を使う。

- 成果物から要件達成を判定する。critical が一つでも未達なら失敗。自己申告の不明瞭点・裁量補完・再試行は補助情報とする。
- 時間や tool 数は実行環境が返す実測値だけ記録する。欠ける値は未取得とし、自己申告や推測で埋めない。
- 失敗した要件と修正の対応を示し、一つの原因に関する修正をまとめて行う。新しい実行者で影響するシナリオを再評価する。
- tool 数や時間の差は調査の手がかりとし、固定倍率だけで欠陥と判定しない。指示に余計な規則を足す前に、対象の成果や判断が改善したかを見る。

## 終了

要件を満たし、追加試行が判断を変えにくくなったら、未使用のシナリオでも確認して終了する。反復しても同じ失敗が残るなら設計を見直す。上限に達したら達成状況と残る不確実性を報告し、無期限に反復しない。

変更、各条件の成果物・採点根拠、改善／悪化、未検証部分をまとめる。新規 subagent が利用できなければ静的レビューは続けられるが、独立した実行評価の代替とは扱わない。盲検比較自体を求められた場合は `double-blind-test` を使う。
