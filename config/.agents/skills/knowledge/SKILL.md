このリポジトリで次に作業する開発者とエージェントが、触る前に読む文書を育てる。置き場所は、学びの種類ごとに 1 つに決まっている。

| 種類 | 置き場所 | 中身 |
|---|---|---|
| 用語 | `GLOSSARY.md` | 語が何を指すか |
| 判断 | `docs/adr/NNNN-*.md` | 覆しにくい決定と、その理由 |
| 実務知 | `docs/knowledge/<topic>.md` | 用語にも ADR にもならない、その領域で作業するときの判断の基準・はまりどころ・確かめ方のコマンド・実測した数字 |

開発ログ（`docs/devlog/`、`devlog` スキル）は時系列の記事で、ここでは素材として読む。知識文書は時系列ではなく、**今の正しい状態**だけを書く。経緯は開発ログと PR に任せ、リンクで辿れるようにする。読み手はリポジトリの中の人なので、issue・PR・ADR・用語集へのリンクで説明を済ませてよい。

## 手順

1. **main を最新にしてブランチを切る。** リポジトリの worktree 規約に従い、`git fetch` して `origin/main` から `docs/knowledge-<slug>` を作る。完了条件: `GLOSSARY.md`（複数の文脈があれば `GLOSSARY-MAP.md` から辿る各用語集）、`docs/adr/`、`docs/knowledge/*.md` を読み終えている。

2. **素材を集める。** 頼まれた範囲の開発ログのエントリを読む。範囲の指定が無ければ、`docs/knowledge/README.md` の「取り込み済み」にまだ載っていない `docs/devlog/*.md` のエントリ全部が対象になる。開発ログの無い作業なら、チケットの本文と resolution コメント、PR の差分、このセッションのやり取り、takt の run（`.takt/runs/*/` の `trace.md`・`reports/`）を直に読む。完了条件: 素材から拾った学びが、1 つずつ箇条書きで手元にある。

3. **振り分ける。** 学びを 1 つずつ、上の表のどれか 1 つに入れる。用語は GLOSSARY に載せる基準（このプロジェクト固有の概念か）、判断は ADR の 3 条件（覆しにくい・文脈なしでは意外・本当にトレードオフがあった）を満たすものだけにし、どちらも満たさないものが実務知になる。他のプロジェクトでも通じる一般論や、コードと設定を見れば分かることは捨てる。完了条件: すべての学びに行き先（または捨てる理由）が付き、既存の用語・ADR・知識文書と食い違うものが洗い出されている。

4. **書く。** 用語と ADR は `domain-modeling` スキルの書式で書き、既存と食い違うものはそちらを直す（ADR は superseded にして新しい番号を立てる）。実務知は、作業する人が「これから触る領域」の名前でトピックを決め、既存の知識文書に足せるならそこに足す。
   - 新しい文書は `# <領域の名前>`、何の作業をするときに読む文書かを書いた 1 段落、関連する用語と ADR へのリンク、の順で始める
   - 節は `##` にし、**見出しを学びの主張そのもの**にする（「モデルが遅いと結論する前に、応答したモデル ID をログで数える」のように）。本文は、その主張の理由と、このプロジェクトでの具体例（数字・コマンド・失敗）1 つ以上
   - 用語集の語は、意味を書き直さずに用語集へリンクする。決定の理由も書き直さずに ADR へリンクする
   - 古くなった記述は、追記で打ち消さずに書き換える
   - 文書の末尾の `## 出典` に、使った開発ログのエントリ（`../devlog/YYYY-MM-DD.md#<slug>`）・PR・issue へのリンクを足す
   - 読んだ素材は、行き先にかかわらず（用語・ADR だけに行ったもの、全部捨てたものも）`docs/knowledge/README.md` の `## 取り込み済み` に 1 行ずつ足す。形は `- <素材へのリンク> → <行き先のリンク、または「捨てた: 理由」>`。手順 2 の「まだ載っていない」はこの節だけで判定する。README が無ければ、`# 知識文書`、知識文書の一覧、`## 取り込み済み` の順で作る

   完了条件: 手順 3 の行き先がすべて書かれ、読んだ素材がすべて「取り込み済み」に載り、食い違いが残っていない。認証情報・個人情報・社外秘の内容が含まれていない。

5. **PR にしてマージする。** リポジトリの検査ゲートを通してからコミットする。コミットと PR のタイトルはリポジトリのコミット規約に従い、規約が無ければ `docs: <何をしたとき>の学びを用語集・ADR・知識文書にまとめる` にする。本文に、触った文書ごとに、足した用語・ADR・節の見出しを箇条書きで並べる。PR を作ってから CI の run が始まるまで数分かかることがある（`gh run list --branch <branch>` で見る）。5 分経っても始まらなければ、PR を閉じて開き直す。リポジトリの規約が人のマージを求めていなければ、auto-merge が有効（`gh api repos/<owner>/<repo> --jq .allow_auto_merge`）なら `gh pr merge <N> --auto --squash` で予約して終え、CI を待たない。無効なら CI が green になってから squash でマージする。完了条件: マージを予約したか済ませていて、PR の URL と、足した用語・ADR・節の一覧を報告している。
