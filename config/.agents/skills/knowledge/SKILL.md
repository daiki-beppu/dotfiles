`docs/knowledge/` は 1 日 1 ファイルの開発ログで、作業ごとに 1 エントリを追記する。日付ファイルは、そのまま技術記事や個人ブログの 1 本として公開する前提で書く。読み手はそのプロジェクトを知らない開発者で、リポジトリが private なら issue や PR のリンク先も読めない。**本文だけで話が通じる**ことを最優先にする。

一次情報で確かめた事実の記録（`docs/research/` など）があるリポジトリでは、そちらは事実、開発ログはその事実で何をどう判断したかを書く。数字や出典は、話の筋に必要な分だけ本文に書き写す（リンク先は読み手に届かない）。

## 手順

1. **main を最新にしてブランチを切る。** リポジトリの worktree 規約に従い、`git fetch` して `origin/main` から `docs/knowledge-<slug>` を作る。完了条件: 既存の開発ログ（`docs/knowledge/*.md`）と、最新の用語集・判断の記録（`GLOSSARY.md`・`docs/adr/` など、そのリポジトリにあるもの）を読み終えている。

2. **素材を集める。** 対象の作業について、チケットの本文と resolution コメント、関連する調査記録と PR の差分、このセッションのやり取りを読む。takt で実装した作業なら、その takt worktree の `.takt/runs/*/` も読む（中心は `trace.md`・`context/task/order.md`・`reports/`。`logs/*.jsonl` は数 MB あるので grep で必要な所だけ）。利用上限などで止まって再開したタスクは run が複数に分かれるので、`.takt/tasks.yaml` の `source_run_slug` → `run_slug` をたどって全部読む。完了条件: 次の 2 つが分かっている。
   - 作業の中で**判断が変わった瞬間**（候補を比べて選んだ、想定と違う結果が出た、決めたことどうしが矛盾した、レビューで差し戻された、思い込みや言い過ぎが外れた）
   - その判断が**その後の main で直されたかどうか**。直されていたら、エントリの最後に「その後」の節を立てて経緯を書く。本文が最新の用語集と食い違ったままにならないようにする

3. **学びを選ぶ。** 学びとは、他のプロジェクトでも使える判断の基準、はまりどころ、再現できるコマンド、実測した数字のこと。決定の中身そのもの（何に決めたか）はチケットにあるので、エントリでは、なぜそう決めたかと、どんな基準で決めたかを書く。完了条件: 学びのそれぞれに、このプロジェクトでの具体例（実際の発言・数字・失敗）が 1 つ以上ある。

4. **書く。** 書いた日（日本時間）の `docs/knowledge/YYYY-MM-DD.md` の末尾に、エントリを 1 つ追記する。既存の日付ファイルがあれば、その形に合わせる。
   - その日のファイルが無ければ作る。冒頭は `# 開発ログ YYYY-MM-DD`、プロジェクトが何かを 1 文で説明する段落、「この日のエントリ:」の番号付きの目次の順に置く。説明の 1 文は、前の日付ファイルにあればそれを使い、無ければ `AGENTS.md`・README・`GLOSSARY.md` から作る。プロジェクトの説明はファイル冒頭の 1 回だけにする
   - 目次に、追記したエントリへのリンクを 1 行足す
   - エントリは `<a id="<slug>"></a>` の行と、`## <タイトル>` の見出しで始める。タイトルは「〜した話」。他のエントリへのリンクは、同じ日なら `#<slug>`、別の日なら `./YYYY-MM-DD.md#<slug>` にする（見出しから自動で作られるアンカーは日本語で崩れやすいので、明示のアンカーを使う）
   - 見出しの直後の 1 段落で、何をしたときの学びかを書き、決定の記録（チケット・ADR）へのリンクを並べる。同じ日のエントリは時系列で並ぶので、直前のエントリへのリンクは要らない
   - 節は `###` の番号付きで、**見出しを学びの主張そのもの**にする（「種別は『答えを出す対象か』という 1 本の軸で切る」のように）。見出しだけを拾い読みしても学びが伝わる
   - プロジェクトの用語（用語集の語）は、エントリの中で初めて出てくるときに一言で説明する。日付ファイルを 1 本だけ読んでも通じるようにする
   - 表・コマンド・数字は、実際に使ったものだけを載せる
   - 判断が外れた場面（思い込み、言い過ぎ、想定と違った結果）は省かずに書く。何を前提にしていて、何で気づいたかまで書くと、開発ログの一番の読みどころになる

   完了条件: 社外秘の内容、個人情報、第三者の発言や文字起こしの長い引用、認証情報が含まれていない。

5. **PR にしてマージする。** リポジトリの検査ゲートを通してからコミットする。コミットと PR のタイトルはリポジトリのコミット規約に従い、規約が無ければ `docs: <何をしたとき>の学びを記録（issue #<n>）` にする。本文に、追記した日付ファイルとエントリのタイトル、節の見出しを箇条書きで並べる。PR を作ってから CI の run が始まるまで数分かかることがある（`gh run list --branch <branch>` で見る）。5 分経っても始まらなければ、PR を閉じて開き直す。CI が green になったら、リポジトリの規約が人のマージを求めていなければ squash でマージする。完了条件: CI が green で、PR の URL と節の一覧を報告している。

## 複数の作業をまとめて書くとき

同じ日の日付ファイルに並行で追記すると、末尾と目次で衝突する。複数の作業（takt の複数の run など）のエントリは、1 つのブランチに作業の順で続けて追記し、1 つの PR にする。素材を読む作業はサブエージェントに分けてよいが、書き込みは 1 か所に集める。
