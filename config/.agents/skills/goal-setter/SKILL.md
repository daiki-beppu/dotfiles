# Goal Setter

ユーザーの求める成果を、達成を証明できる短い目標にする。下書き・監査・有効化のどれを求められているかに従い、下書き依頼だけで有効化しない。

## 目標を定める

会話と必要な資料から、求める成果、達成の証拠、変えてはいけない境界を特定する。調査で分かる情報は調べ、成果や範囲を変える未決事項だけ確認する。軽微で可逆な選択は仮定を示して進める。

目標はタスクの言葉で、最終状態とその検証を先に書く。実装順や定型的なファイル一覧は実行者に任せる。ユーザーが求める実物の代わりに、モック・雛形・仮データを完了条件にしない。

- **成果と証拠**: 何ができれば完了か、どこで確認するか。既存の検証を使い、必要な証拠がなければそれを用意する作業を含める。
- **制約と権限**: 今回の範囲、守る互換性、データや公開操作の実際の境界。既存承認を再確認の条件に置き換えない。
- **継続と終了**: 必要な実装・実行確認・修復を含め、未完了なら続ける。必須の情報・権限・外部サービスが欠けた場合は証拠と最小の次の対応を報告する。完了条件を弱めて成功にしない。

通常は一文か短い段落で足りる。複雑な案件で証拠や範囲を定める必要があるときだけ [成果別の検証](references/verification.md) を読む。一般的な注意事項をすべて目標へコピーしない。

## 監査・有効化

既存目標の監査では、依頼した成果が欠けていないか、検証可能か、不要な固定手順や途中停止がないかを確認し、修正版を示す。

有効化を明示的に依頼された場合は実行環境のネイティブな目標ツールを使う。既存目標があれば状態を確認し、実行中の別目標を勝手に置換しない。ツールがなければ `/goal …` を提示し、ユーザーによる送信が必要と伝える。成功応答を得た場合だけ設定済みと報告する。

トークン予算は指定された場合だけ設定する。文字数上限のある `/goal` を出力するときは [validate_goal_length.py](scripts/validate_goal_length.py) で確認する。4,000 文字の検査上限は品質目標ではなく、実行環境に別の上限があればそちらを使う。

並列作業は現在の環境の権限とツールに従う。目標の有無だけで subagent の権限や起動可否を決めない。別のユーザー所有タスク作成は、それ自体を依頼された場合に限る。
