# Issue

会話とリポジトリの事実から、実装者が単独で着手できる issue を作成する。起票と整理を扱い、実装や takt 実行は含めない。

## モード

- 通常: 内容を調べ、未決事項があれば確認して起票する。
- `--organize`: [既存 issue の整理](references/organize.md) だけを読む。
- `--dry-run`: 作成・変更の直前まで調べ、対象と本文・関係の変更案を提示する。GitHub は変更しない。
- `--no-interview`: 会話と調査から本文を作り、埋まらない項目は未確定と記す。「そのまま作って」「おまかせ」も同様に扱う。
- `--split` / `--no-split`: 分割する／一件にまとめる。
- `--parent <N>`: 指定親の native sub-issue にする。`--label <name>`: 実在を確認して指定ラベルを使う。

Wayfinder 完了後の実装起票は、リポジトリの `to-spec` → `to-tickets` 規約に従う。

## 内容を確定する

対象リポジトリを確認し、キーワードで類似 issue を検索する。直近の一覧だけで重複なしと判断しない。重複候補の同一性を調べ、それでも新規作成か既存利用か決められない場合だけ確認する。

対象に関連する実装・兄弟入口・テスト・品質ゲートと issue template を調べる。起票のために全体の文書を読み込んだり、品質ゲートを実行したりする必要はない。

目的、期待結果、範囲、受け入れ条件を会話から復元する。結果を変える未決事項だけ質問し、合意済みの事項を聞き直さない。必要なインタビューでは一度に一問とする。`--no-interview` は未知を捏造せず本文で区別する。

## 本文と分割

本文生成時に [body-contract.md](references/body-contract.md) を読む。リポジトリのテンプレートを優先しつつ、takt が必要とする `概要`・`目的`・`受け入れ条件` と検証可能な完了契約を保持する。

一つの issue で何が変わるかを一文で説明できる粒度を目安にする。独立した振る舞いが複数あり分割が必要な場合や `--split` 指定では [splitting.md](references/splitting.md) を読む。ユーザーの指定範囲を優先し、`--no-split` なら混在する振る舞いを報告する。

タイトルは日本語で具体的にする。ラベルは既存の実在名を使い、作成を依頼されていない新規ラベルや、実行を起動する `takt:*` 等のラベルを追加しない。

## 作成と完了

対象・タイトル・ラベル・本文を具体化したら、起票依頼の範囲で作成する。内容が確定していれば再承認を挟まない。調査中に範囲が変わった場合は重複確認を更新する。`--dry-run` は作成前に止める。

本文はシェル展開されない方法でファイルへ書き、`gh issue create` / `edit` に `--body-file` で渡す。親への接続は [native sub-issue の接続](references/parent.md) を参照する。分割の依存関係は splitting の手順に従う。

作成した issue の URL と番号、要求された親子・blocking 関係を取得して確認する。応答が不明な操作は既存状態を照合してから再試行し、重複作成を避ける。URL、関係、未確定項目を報告する。

issue 本文は takt 投入時に order.md へコピーされる。投入後の本文編集は既存タスクへ自動反映されないため、再投入が必要なら `takt` で扱う。
