# issue

会話コンテキストとリポジトリの事実から、実装者が単独で着手できる GitHub issue を作成する。

## 実行スタイル

- **調査は自分で行う**: リポジトリ調査を subagent に委任しない。数回のツール呼び出しで済む範囲であり、委任するとインタビュー開始が遅れる。委任してよいのは影響範囲がリポジトリ全域に及び並行探索が明確に速い場合だけで、そのときも1体に留める
- **スコープ**: 起票と `--organize` の範囲に限定する。実装は issue-implement / takt の責務。
- **進め方**: 発見できる事実は調査で埋め、質問は成果・範囲・受け入れ条件を変える未決事項に絞る。完了報告は作成結果と残る未確定事項を簡潔に示す
- **完了報告は結論から**: 作成した issue の URL とタイトルを先に述べる。本文の内容を会話に再掲しない

## Invocation variants

- Bare / 起票したい内容 → フェーズ 1〜6 を通す(インタビュー → 起票)。
- `--organize` → 起票ではなく既存 open issue 群の再構造化。フェーズ 1〜6 は通らず、
  [references/organize.md](references/organize.md) を読んでその手順だけに従う。
- `--dry-run` → フェーズ 6 の直前で止め、リポジトリ・カテゴリ・タイトル・ラベル・本文を
  提示するだけで `gh issue create` を叩かない。フェーズ 1〜5 は通常どおり行う。
- `--no-interview` → フェーズ 2 を省略し、会話コンテキストと調査結果だけで本文を作る。
  埋まらない項目は捏造せず「未確定」と明記する。**重複確認(フェーズ 1)は省略しない**。
- `--split` → 分割判定を省略して分割する側に倒す。依存順に複数起票し `addBlockedBy` を張る。
- `--no-split` → 1件に押し込む。ただし振る舞いが2つ以上あると判定した場合は、
  **押し込んだ旨と混ざった振る舞いを完了報告に明記する**(黙って1件にしない)。
- `--parent <N>` → 指定した親 issue の sub-issue として作成する(フェーズ 6)。
- `--label <name>` → ラベルを明示する。既存ラベルとの照合は省略しない。

## フェーズ 1: コンテキストを収集する

```bash
gh repo view --json nameWithOwner
git branch --show-current
gh label list --json name,description,color
gh issue list --limit 30 --state all --json number,title,state,labels
```

あわせて `AGENTS.md` / `CLAUDE.md`、README、CI workflow、package manifest、`Makefile` などを読み、以下を実コードから特定する。

- 関連する既存実装とテスト
- 変更が波及する兄弟入口や設定経路
- lint / test / typecheck などの品質ゲート
- `.github/ISSUE_TEMPLATE/` の有無（テンプレートがあるリポジトリではその構成を優先し、本スキルの出力契約から不足分だけ補う）

存在しないファイルやコマンドを推測しない。起票時には品質ゲートを実行せず、実装完了時の受け入れ条件として記録する。

### 重複を先に確認する

インタビューを始める前にキーワード検索で類似 issue を探す。`gh issue list --limit 30` だけでは直近分しか見えない。

```bash
gh search issues --repo <owner/repo> "<起票内容のキーワード>" --limit 10
```

類似 issue が見つかったらユーザーに提示し、新規作成を続けるか判断を仰ぐ。既存 issue へのコメント追加は行わない。

## フェーズ 2: 内容を合意する

本文生成前に、会話と調査で未決の方針・境界・期待結果を確認する。既に揃っていれば本文生成へ進む。`--no-interview` ではこのフェーズに入らない。

- 質問が必要なときだけ一度に1問聞く
- 調査結果から推奨回答を提示し、Yes / No / 修正で答えられる形にする
- AskUserQuestion ツールが使える環境ではそれを使い、推奨案を先頭の選択肢にして「(Recommended)」を付ける。選択式にできない自由記述の質問だけテキストで聞く
- ファイルパスや既存挙動などの事実は自分で調べ、ユーザーには方針・境界・期待結果だけを聞く
- 会話ですでに合意済みの事項は聞き直さない

次の順で必要な項目だけ確認する。

1. 目的と解決したい問題
2. カテゴリ
3. 再現手順または提案仕様
4. 検証可能な受け入れ条件
5. スコープ外
6. 影響範囲と兄弟入口
7. 品質ゲート
8. 設計判断がある場合のアプローチ
9. 分割方針（振る舞いが2つ以上に見えるなら必ず確認する。分割する場合はスタックの積み順もあわせて合意する）

ユーザーが「そのまま作って」「対話なしで」「おまかせ」と明示した場合、またはタイトルと本文が完全指定されている場合も `--no-interview` と同じ扱いにする。

## フェーズ 3: カテゴリを決める

| カテゴリ | 用途 | 標準ラベル |
|---|---|---|
| `bug` | 不具合報告 | `bug` |
| `feature` | 新機能・機能改善 | `enhancement` |
| `refactor` | 挙動を変えない内部改善 | `refactor` |
| `chore` | 依存更新・設定・雑務 | `chore` |
| `docs` | ドキュメント更新 | `documentation` |

複数該当する場合は主カテゴリを1つ選び、補助カテゴリは追加ラベルで表す。該当しない案件はユーザーと合意した汎用構成を使う。

## フェーズ 4: 本文を生成する

本文は [references/body-contract.md](references/body-contract.md) の出力契約に**逐語で従う**。
生成の前に必ず全文を読む(テンプレート・書式規約・要件/完了契約の書き方。
`概要` `目的` `受け入れ条件` を常置する理由もそこにある — 省くと takt 互換が壊れる)。

### 粒度: 1 issue = 1 振る舞い

**1 issue = 1 振る舞い = 1 PR = スタック1段**。`--no-split` の扱いは Invocation variants、準備段の例外は splitting.md に従う。判定は次の一文で行う。

> この issue を完了させたとき、**利用者または呼び出し側から見て何が1つ変わるか**を1文で言い切れるか。

言い切れない・分割で合意した・`--split` 指定のときは、
[references/splitting.md](references/splitting.md) に従って分割を設計する
(分割後の形 / 準備段の例外 / expand–contract / addBlockedBy)。**分割するときは必ず読む**。

## フェーズ 5: タイトルとラベルを決める

- タイトルは日本語で簡潔かつ具体的にする
- 過去issueのラベル運用と既存ラベルの description を確認する
- カテゴリに対応する既存ラベルを優先し、綴りを実在名に合わせる。存在しないラベルを渡すと issue 作成自体が失敗する
- 適切な既存ラベルがない場合だけ、インタビュー中に新規ラベルを提案する
- ユーザーの承認なしに `gh label create` を実行しない
- `takt:*` などの workflow・自動化トリガー用ラベルは付与しない。過去 issue でその運用が見えても従わない（着手方式の判断は起票後に行う）

確定タイトルで既存 issue と再度照合する。インタビュー中にスコープが変わっている場合があるため、冒頭の重複確認とは別に最終ガードとして行う。類似 issue があれば新規作成前にユーザーへ確認する。

## フェーズ 6: プレビューして作成する

リポジトリ、カテゴリ、タイトル、品質ゲート、ラベルと本文をプレビューする。インタビューの合意、または `--no-interview` に相当する作成依頼を承認として、類似 issue や未決の重要事項がなければ追加確認なしで作成する。`--dry-run` はここで止める。

本文はテーブルとバッククォートを多く含むため、quoted heredoc (`<<'BODY'`) でファイルへ書き、**`--body-file` を使う**。バッククォートや `$` のシェル展開を防ぐため、`gh issue edit` も同様にする。

```bash
cat > /tmp/issue-body.md <<'BODY'
## 概要
...
BODY

gh issue create --title "タイトル" --body-file /tmp/issue-body.md --label "label1,label2"
```

`--parent <N>` が指定された場合は、作成後に GraphQL で親へ接続する。

```bash
PARENT_ID=$(gh api repos/$OWNER/$REPO/issues/<親番号> --jq '.node_id')
CHILD_ID=$(gh api repos/$OWNER/$REPO/issues/<作成した番号> --jq '.node_id')
gh api graphql -f query="mutation {
  addSubIssue(input: { issueId: \"$PARENT_ID\", subIssueId: \"$CHILD_ID\" }) {
    issue { number } subIssue { number }
  }
}"
```

作成応答の URL と番号を確認して完了とする。親子・依存関係を要求された場合は接続結果も確認する。失敗した操作だけ原因を調べ、再試行前に既存作成の有無を確認して重複を防ぐ。修正依頼には `gh issue edit --body-file` で追従する。

## 完了報告

報告するもの:

1. 作成した issue の URL とタイトル(分割した場合は**依存順に下段から**全件)
2. カテゴリと付与したラベル
3. 張った `blockedBy` 依存(= スタックの積み順)。`--parent` を使ったなら親への接続
4. 重複確認で見つかった類似 issue と、それでも新規作成した理由(あれば)
5. `--no-split` で押し込んだ場合は、混ざっている振る舞い
6. 品質ゲートを特定できず本文に「未確定」と書いた項目(あれば)

本文の内容は会話に再掲しない。**次に takt へ積むか自分で実装するかは提案しない**(着手方式の判断は起票の外)。

## 本文確定後の注意

issue 本文は takt 投入時に order.md へコピーされる。投入後の本文修正は実行中・実行済みタスクへ伝播しない。積み直しが必要なら takt スキルの責務とする。
