# Codex Cloud setup

完了条件は、対象環境の保存を画面で確認し、その最終設定でセットアップ・メンテナンスとプロジェクトの動作を Cloud 上で検証したこと。設定案の提示やボタンのクリックだけで完了にしない。

## 1. 仕様とリポジトリを確定する

- [公式 Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environment) を毎回開き、ランタイム、スクリプト、キャッシュ、変数・Secrets の現行仕様を確認する。通信設定を変える場合は同ページから現行の Internet access 文書も読む。記憶と画面が違えば現行仕様を優先する。
- Git remote から所有者とリポジトリを特定する。認証情報を含む URL は伏せる。最新のリモート main（別名なら実際のデフォルトブランチ）を fetch し、その SHA の AGENTS.md、マニフェスト、ワークスペース・カタログ、ロックファイル、CI、実行スクリプトを読む。
- ローカルとの差分を把握し、未コミット変更を保持する。Cloud 設定だけのためにローカルコードを変更しない。未 push の構成を Cloud が取得できるものとして扱わない。
- 構成の根拠、ランタイム制約、依存導入コマンド、チェック・テスト・ビルドと必要な実行時依存を特定できたら次へ進む。名前・パス・バージョンを過去のプロジェクトから固定コピーしない。

## 2. 対象環境を開く

利用可能なブラウザー操作ツールと接続を確認し、接続済みの手段で設定画面を操作する。通常操作はネイティブのブラウザーツールを優先し、接続不能なら利用可能な別のブラウザー操作手段へ切り替える。ツールの使用規約に従い、画面で確認した要素を使う。

環境一覧でアカウント／ワークスペースとリポジトリを照合し、既存環境があれば更新、なければ作成する。複数候補の用途が判別できなければ対象だけ質問する。作成・保存の結果が不明なときは一覧を再確認してから再試行し、重複を作らない。接続やログインを解消できなければ必要なユーザー操作を具体的に伝える。

## 3. 設定する

既存値を確認し、対象リポジトリに必要な項目を更新する。

- ランタイムはリポジトリの制約と Cloud の選択肢から決める。自動セットアップで充足しなければ手動スクリプトを設定する。
- セットアップは初期導入、メンテナンスはキャッシュ復元後のチェックアウトに対する依存の再同期として設計する。ロックを尊重し、再実行可能にする。キャッシュの有無・無効化条件を現行仕様で確認し、必要ならリセットして初回経路も検証する。
- Node.js／Vite+、または Playwright・PDF 生成がある場合は [構成別の注意点](references/runtime-validation.md) を読んで設定・検証する。
- Secrets はセットアップ段階だけ、環境変数はエージェント段階にも残る。必要な利用段階に合わせて配置する。値は出力せず、名前と有無だけ扱う。他プロジェクトのトークンを無断で流用しない。
- セットアップ内の `export` はエージェント段階へ永続化されない。PATH を含め必要な値を環境設定等で持続させ、後続の独立したシェルで確認する。
- インターネットアクセスや権限の拡張は必要な通信先・操作を特定し、適用される承認ルールに従う。依頼済みの通常の作成・更新・テスト・保存には不要な再確認を挟まない。

## 4. Cloud で検証する

対話型テストを開始し、初期セットアップとメンテナンスの各終了状態を確認する。メンテナンスが不要なら、その理由を記録する。

大量の導入ログは Cloud 内のファイルへ保存し、失敗時は秘密値を除いた末尾と終了コードを表示する。アクセシビリティツリーは長いログを省略するため、「変化なし」だけでは停止と判断しない。使用ツールで許可された DOM snapshot、ログ領域の末尾取得やスクロールで最新行・状態を確認する。観測できるエラーに対処して再試験し、同じ失敗を根拠なく繰り返さない。

`Test complete` または現行 UI の同等の完了表示と、各処理の成功を両方確認する。その後、Cloud のセットアップ後の独立したシェルで、作業ディレクトリ、チェックアウト SHA、実際のランタイム、PATH とツールの利用可否を確認する。単なる子シェルは親の export を継承するため、永続化の証拠にはしない。

調査済みのチェック・テスト・ビルドを Cloud 内で実行し、終了コードと結果を記録する。必要なブラウザーやサービスも実際に起動し、生成物やヘルスチェックを確認する。確認用プロセスは終了する。UI で独立シェルや復元経路を検証できない場合は未検証と明記し、実装タスクを代わりに起動しない。

失敗は環境の問題と既存コードの問題に分ける。環境の問題は設定を修正して該当経路を再検証する。テスト未配置は「未配置」、既存警告は警告として報告し、成功件数に数えない。環境設定の依頼にはコード修正・実装タスクの起動・デプロイ・公開を含めない。

## 5. 保存と報告

画面の順序に応じて作成・保存を行い、保存成功の表示を確認する。環境を開き直し、対象リポジトリと最終設定の保持を照合する。テスト後に設定を変更したら影響する検証をやり直す。完了表示が不明なら保存済みと断言しない。

報告には環境リンク、作成／更新、対象 SHA、主な設定、セットアップ／メンテナンス、実測バージョンとプロジェクト検証結果を含める。成功・未配置・既存警告／失敗・環境構築失敗・未検証を区別し、障害が残る場合は保存状態と未完了部分を明示する。
