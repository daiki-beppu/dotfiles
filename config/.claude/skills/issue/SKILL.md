# issue

会話コンテキストとリポジトリの事実から、実装者が単独で着手できる GitHub issue を作成する。

## 概要

起票の成果物は**本文という1つのレポート**であり、その構造は takt の出力契約に従う。

設計の骨子:

- **本文は takt の `base-plan` 出力契約に揃える**。takt に積むと issue 本文がそのまま
  order.md に書き込まれ、plan step の入力になる。語彙と構造が揃っていれば planner が
  読み替えずに済む。書式規約の正本は takt の `OUTPUT_CONTRACT_STYLE_GUIDE.md`
  (`{簡潔な説明}` プレースホルダー / 場所は `` `file:line` `` / 構造化データはテーブル /
  実行手順は書かない)
- **要件と完了契約を分ける**。要件は「何が変わるか」、完了契約は「何をもって成立とし、
  何を誤実装として拒否するか」。実装者と reviewer が見るのは後者
- **1 issue = 1 振る舞い = 1 PR = スタック1段**。分割したら `addBlockedBy` で依存を張り、
  その依存チェーンがそのままスタックの積み順になる
- **起票以外の GitHub 操作へ広げない**。既存 issue の編集・クローズ・ラベル整理はしない
  (整理は issue-organize、実装は issue-direct / takt の責務)

## 実行スタイル

- **調査は自分で行う**: リポジトリ調査を subagent に委任しない。数回のツール呼び出しで済む範囲であり、委任するとインタビュー開始が遅れる。委任してよいのは影響範囲がリポジトリ全域に及び並行探索が明確に速い場合だけで、そのときも1体に留める
- **実況しない**: インタビュー中は質問だけを出し、調査の途中経過や検討過程を逐一書かない
- **完了報告は結論から**: 作成した issue の URL とタイトルを先に述べる。本文の内容を会話に再掲しない

## Invocation variants

- Bare / 起票したい内容 → フェーズ 1〜6 を通す(インタビュー → 起票)。
- `--dry-run` → フェーズ 6 の直前で止め、リポジトリ・カテゴリ・タイトル・ラベル・本文を
  提示するだけで `gh issue create` を叩かない。フェーズ 1〜5 は通常どおり行う。
- `--no-interview` → フェーズ 2 を省略し、会話コンテキストと調査結果だけで本文を作る。
  埋まらない項目は捏造せず「未確定」と明記する。**重複確認(フェーズ 1)は省略しない**。
- `--split` → 分割判定を省略して分割する側に倒す。依存順に複数起票し `addBlockedBy` を張る。
- `--no-split` → 1件に押し込む。ただし振る舞いが2つ以上あると判定した場合は、
  **押し込んだ旨と混ざった振る舞いを完了報告に明記する**(黙って1件にしない)。
- `--parent <N>` → 指定した親 issue の sub-issue として作成する(フェーズ 6)。
- `--label <name>` → ラベルを明示する。既存ラベルとの照合は省略しない。

## フェーズ 1: コンテキストを収集する

```bash
gh repo view --json nameWithOwner
git branch --show-current
gh label list --json name,description,color
gh issue list --limit 30 --state all --json number,title,state,labels
```

あわせて `AGENTS.md` / `CLAUDE.md`、README、CI workflow、package manifest、`Makefile` などを読み、以下を実コードから特定する。

- 関連する既存実装とテスト
- 変更が波及する兄弟入口や設定経路
- lint / test / typecheck などの品質ゲート
- `.github/ISSUE_TEMPLATE/` の有無（テンプレートがあるリポジトリではその構成を優先し、本スキルの出力契約から不足分だけ補う）

存在しないファイルやコマンドを推測しない。起票時には品質ゲートを実行せず、実装完了時の受け入れ条件として記録する。

### 重複を先に確認する

インタビューを始める前に類似 issue を探す。重複だと判明するのが遅いほど、それまでの質問が無駄になる。

```bash
gh search issues --repo <owner/repo> "<起票内容のキーワード>" --limit 10
```

類似 issue が見つかったらユーザーに提示し、新規作成を続けるか判断を仰ぐ。既存 issue へのコメント追加は行わない。

## フェーズ 2: 内容を合意する

本文生成前に、grilling スタイルでユーザーと合意する。`--no-interview` ではこのフェーズに入らない。

- 一度に1問だけ聞く
- 調査結果から推奨回答を提示し、Yes / No / 修正で答えられる形にする
- AskUserQuestion ツールが使える環境ではそれを使い、推奨案を先頭の選択肢にして「(Recommended)」を付ける。選択式にできない自由記述の質問だけテキストで聞く
- ファイルパスや既存挙動などの事実は自分で調べ、ユーザーには方針・境界・期待結果だけを聞く
- 会話ですでに合意済みの事項は聞き直さない

次の順で必要な項目だけ確認する。

1. 目的と解決したい問題
2. カテゴリ
3. 再現手順または提案仕様
4. 検証可能な受け入れ条件
5. スコープ外
6. 影響範囲と兄弟入口
7. 品質ゲート
8. 設計判断がある場合のアプローチ
9. 分割方針（振る舞いが2つ以上に見えるなら必ず確認する。分割する場合はスタックの積み順もあわせて合意する）

ユーザーが「そのまま作って」「対話なしで」「おまかせ」と明示した場合、またはタイトルと本文が完全指定されている場合も `--no-interview` と同じ扱いにする。

## フェーズ 3: カテゴリを決める

| カテゴリ | 用途 | 標準ラベル |
|---|---|---|
| `bug` | 不具合報告 | `bug` |
| `feature` | 新機能・機能改善 | `enhancement` |
| `refactor` | 挙動を変えない内部改善 | `refactor` |
| `chore` | 依存更新・設定・雑務 | `chore` |
| `docs` | ドキュメント更新 | `documentation` |

複数該当する場合は主カテゴリを1つ選び、補助カテゴリは追加ラベルで表す。該当しない案件はユーザーと合意した汎用構成を使う。

## フェーズ 4: 本文を生成する（出力契約）

次の出力契約に従う。**条件付きの見出しは、条件に当てはまらなければ見出しごと省く**。該当のないセクション・要件の言い換え・締めの定型文で膨らませない。

```markdown
## 概要
{何を・なぜ行うかを1-3文}

## 背景・目的（複雑な背景がある場合のみ）
{経緯と、いま解決すべき理由}

<!-- カテゴリ固有セクション -->

## 検討したアプローチ（設計判断がある場合）
| アプローチ | 採否 | 理由 |
|-----------|------|------|
| {案} | 採用 / 不採用 | {理由} |

## 参照資料（あれば）
- `path/to/file:42` — {何を参照するか}

## 影響ファイル
| 種別 | ファイル | 概要 |
|------|---------|------|
| 作成 | `src/new.ts` | {概要} |
| 変更 | `src/existing.ts:88` | {概要} |
| 削除 | `src/old.ts` | {概要} |

### 兄弟入口・貫通先
| 入口 | 変更要否 | 理由 |
|------|----------|------|
| `src/cli.ts:120` | 要 / 不要 | {不要の場合は現行コードの根拠を `file:line` で} |

## 要件
| # | 要件 | 変更要否 | 種別 | 由来・導出根拠 | 備考 |
|---|------|----------|------|----------------|------|
| 1 | {検証可能な最小単位の要件} | 要 / 不要 — 不要の場合は現行コードの根拠を `file:line` で記載 | 明示 / 直接導出 / 維持 | {合意した指示 / 導出の理由 / 維持する既存契約の `file:line`} | {複合要件を分解した場合の補足} |

## 完了契約
| 契約ID | 要求・維持事項 | 由来 | 成立する振る舞い | 拒否すべき誤実装 | 実装箇所 | 完了証拠 |
|--------|----------------|------|------------------|------------------|----------|----------|
| `{安定ID}` | {明示要求、直接導出した要求、または変更対象外として維持する観測可能な既存契約} | {要件テーブルの行と根拠} | {観測可能な成功条件} | {もっともらしい反例} | {変更候補} | {観測方法と検証レイヤー} |

### 影響経路（該当する契約のみ）
| 契約ID | 定義・生成 | 変換・保存・復元 | 消費・出力・補助入口 | 状態・所有権 | 現行利用側の移行 | 明示された支援 |
|--------|------------|------------------|---------------------|-------------|------------------|------------------|
| `{同じ安定ID}` | {定義元と生成元} | {実在する中間経路} | {全消費元と入口} | {状態・所有権} | {置換時に新契約へ移す利用側} | {要求された場合だけ対象・範囲} |

## 位置づけ（スタックの段に載せる場合のみ）
- 段: {N段目 / 単独}
- 積み増し先 PR: {#番号 / なし}

## スコープ外
| 項目 | 除外理由 |
|------|---------|

## 受け入れ条件
- [ ] `{lint command}` が exit 0 になる
- [ ] `{test command}` が成功する
```

依存関係(`Blocked by`)は本文に書かない。GitHub ネイティブの blocking 関係として登録する(後述)。ただし**段番号と積み増し先 PR は `位置づけ` に書く** — takt に積むと order.md へ入るのは本文だけで `blockedBy` は伝播しないため、これらは本文に持たないと実装者へ届かない。依存 issue の番号列は書かない(正は `addBlockedBy` 側)。

カテゴリ固有セクションは次を使う。

- `bug`: `再現手順`、`期待される動作`、`実際の動作`、`影響範囲`
- `feature`: `提案する仕様`、`ユースケース`
- `refactor`: `現状の問題`、`あるべき状態`、`制約`
- `docs`: `対象`、`想定読者`、`更新方針`
- `chore`: 固有セクションなし

### 書式規約

takt の `OUTPUT_CONTRACT_STYLE_GUIDE.md` に従う。

| 規約 | 内容 |
|---|---|
| プレースホルダー | `{簡潔な説明}`。「ここに〜を書いてください」のような冗長な指示文にしない |
| 場所 | `` `src/file.ts:42` `` 形式。自然言語で場所を説明しない |
| 構造化データ | テーブルで表す。箇条書きの入れ子で複雑な構造を作らない |
| 種別カラム | 影響ファイルは 作成 / 変更 / 削除、要件の種別は 明示 / 直接導出 / 維持、変更要否は 要 / 不要 |
| 分量 | 説明の地の文はテーブル行を除き30行以内 |
| 書いてはいけないもの | 実行手順(「まず〜を確認し」)、判断基準の詳細、着手方式のルーティング |

### 要件の書き方

要件は1行に1つの観測可能な結果を書く。`A/B`、`global/project`、`allow/deny`、`read/write`、作成・更新・削除などの並列条件は別行に分ける。「改善する」「対応する」だけの測定不能な要件を書かない。

種別は要件の出どころを表す。

| 種別 | 意味 |
|---|---|
| `明示` | 会話で合意した要求そのもの |
| `直接導出` | 明示要求の成立に不可欠な導出。導出の理由を由来欄に書く |
| `維持` | 変更対象外にある観測可能な既存契約。壊してはいけないものを回帰要件として固定する |

変更要否が `不要` の要件(`維持` が典型)は、現行コードの根拠を `` `file:line` `` で必ず添える。根拠を示せない「たぶん今もそうなっている」を維持要件にしない。

会話にも既存契約にも根拠がない項目は要件にしない。設計上の好みは `検討したアプローチ` へ、未確定は `スコープ外` かインタビューの追加質問へ回す。

### 完了契約の書き方

完了契約は要件を「実装者が満たしたと言い張れない形」に落としたもの。要件テーブルと1対1にはしなくてよく、**外から観測できる単位**でまとめる。

- **契約ID は内容を表す小文字ハイフン区切りの slug**(`preserve-global-scope` / `reject-empty-body`)。
  行番号や連番にしない — 行を挿し込むたびに ID がずれ、takt の後続 step から参照できなくなる
- **由来には対応する要件テーブルの行と根拠を書く**。要件に由来を持たない契約を作らない
- **拒否すべき誤実装を必ず書く**。「もっともらしいが要求を満たさない実装」を1つ挙げる。
  ここが空の契約は、実装者が最短経路で通してしまう
- **完了証拠は観測方法と検証レイヤー**(unit / integration / E2E / 手動手順)を書く。
  「テストを追加する」だけでは証拠にならない
- **置換を含む場合は、現行利用側の移行と旧経路の削除を別々の契約行にする**。
  1行に押し込むと、片方だけ満たした実装を拒否できない
- **維持義務が特定の入力・モード・状態・入口だけに適用されるなら、契約を適用範囲ごとに分ける**。
  ソースが選択肢を開いたままにしている範囲へ、現行動作や採用案を拡張して固定しない

`受け入れ条件` との違い: 完了証拠は契約ごとの観測方法、受け入れ条件は issue 全体で通すリポジトリ共通の品質ゲート。両者を混ぜない。

### 粒度: 1 issue = 1 振る舞い

**1 issue = 1 振る舞い = 1 PR = スタック1段** を粒度の単位とする。

**振る舞い**とは、外から観測できる挙動の変化を1つ指す。要件テーブルの1行(検証可能な最小単位)と、それを固定する完了契約の「成立する振る舞い」に対応する。内部構造だけを変えて観測結果が変わらないものは振る舞いではない。

判定は次の一文で行う。

> この issue を完了させたとき、**利用者または呼び出し側から見て何が1つ変わるか**を1文で言い切れるか。

「〜と〜ができるようになる」「〜を直しつつ〜も追加する」のように接続詞で繋がなければ言えないなら、繋いだ数だけ issue に割る。

次は量的な代理指標で、超えたら振る舞いが複数混ざっている疑いが濃い。単独では分割理由にならないため、該当したら上の一文を言い切れるか問い直す。

| 指標 | 閾値 | 強さ |
|---|---|---|
| 要件の件数 | 2件以上 | 強い(要件1行 = 1振る舞いのため) |
| 独立した機能領域・関心事 | 2つ以上混在 | 強い |
| 影響ファイル数 | 4件以上 | 弱い(1つの振る舞いが広く波及することはある) |

「実装が複数 PR に分かれそう」はスタック前提では分割の理由ではなく**結果**である。複数段に分かれること自体は正常なので、それを避けるために1 issue へ押し戻さない。

判断に迷う場合も分割案を提示する側に倒す。分割で合意した場合は親 issue を本スキルで作成し、子 issue の作成と GraphQL `addSubIssue` での親子接続は issue-organize スキルの手順に従う。

### 分割後の1件が満たすべき形

分割して得た各 issue は、次を満たすこと。

- **振る舞いが1つ閉じる**: その issue だけを完了させた時点で、宣言した1つの振る舞いを実演または検証できる
- **全レイヤを貫く**: schema / API / UI / テストを縦に貫通する狭い完全な経路にする。振る舞いを閉じるには通常これが必要になるため、1レイヤだけを横に切った issue にしない
- **1 context に収まる**: 新規セッション1本で実装しきれる分量に収める
- **prefactor を先に置く**: 実装を楽にする下準備が必要なら、それを先行 issue として独立させる(振る舞いを持たない下準備は下の例外に従う)

#### 例外: 振る舞いを持たない準備段

schema の追加、共通ユーティリティの新設、後述の expand フェーズのように、**それ自体では観測できる挙動が変わらない**変更がある。これらは「1 issue = 1 振る舞い」を満たさないが、次を**すべて**満たす場合に限り独立した issue にしてよい。

- スタックの**下段**に置く
- それを消費して振る舞いを閉じる**上段 issue を同時に起票する**
- 上段から下段へ `addBlockedBy` で依存を張る
- 下段単体で CI green を保てる(旧い形を壊さず**隣に**足すだけにする)

上段を伴わない準備段は起票しない。上段が存在しないまま準備段だけが main に入ると、誰も呼ばないコードが残る。上段に何を載せるか決まっていない段階は、準備段の起票そのものが早い。

### Blocked by（依存関係）を付ける

各 issue に、**着手前に完了している必要がある issue** を依存関係として登録する。sub-issue の親子は階層であって依存関係ではないため、両方を持たせる。

**GitHub ネイティブの blocking 関係(`addBlockedBy`)を必ず使う。** 本文には書かない — 2箇所に持つと必ず食い違うため、ネイティブ側を唯一の正とする。`gh issue` に依存関係のサブコマンドは無いので GraphQL を使う。

作成順は**依存順(blocker が先)**にする。`addBlockedBy` は issue の node ID を要求するため、blocker が既に存在していないと接続できない。

```bash
# 1. 双方の node ID を取得(gh issue view の id がそのまま GraphQL node ID)
BLOCKED_ID=$(gh issue view <塞がれる側の番号> --json id --jq .id)
BLOCKER_ID=$(gh issue view <塞ぐ側の番号> --json id --jq .id)

# 2. 依存を登録
gh api graphql -f query='
mutation($issueId:ID!,$blockingIssueId:ID!){
  addBlockedBy(input:{issueId:$issueId, blockingIssueId:$blockingIssueId}){
    issue{ number issueDependenciesSummary{ totalBlockedBy } }
  }
}' -F issueId="$BLOCKED_ID" -F blockingIssueId="$BLOCKER_ID"
```

`addBlockedBy` の応答に含まれる `totalBlockedBy` が結果の確認そのものなので、成功応答が返ったら追加の照会はしない。応答が意図と違うとき、または複数 issue を張り終えて依存グラフ全体を見たいときだけ照会する。

```bash
gh api graphql -f query='
query($owner:String!,$repo:String!,$num:Int!){
  repository(owner:$owner,name:$repo){
    issue(number:$num){ blockedBy(first:50){ nodes{ number title state } } }
  }
}' -F owner=<owner> -F repo=<repo> -F num=<番号>
```

着手は **frontier** — `blockedBy` が空、または全 blocker が `CLOSED` の issue — から選ぶ。直列に繋がっている場合は上から順になる。

誤って張った依存は `removeBlockedBy` を同じ引数で呼べば外せる。

### 依存チェーンはそのままスタックの積み順になる

分割で得た issue 群の `blockedBy` チェーンは、実装時に gh-stack のスタック構造そのものになる。起票の段階でスタックを設計していることを意識する。

```
main (trunk)
 └── #12 (blockedBy: なし)  → 1段目・PR base = main
  └── #13 (blockedBy: #12)  → 2段目・PR base = #12 のブランチ
   └── #14 (blockedBy: #13) → 3段目
```

- **直列に置けるものは直列にする**: 並列な blocker は積み順が一意に決まらず、スタックに落とす時点で順序を決め直すことになる。実装順に意味があるなら直列の依存を張る
- **1つのスタックは1つのストーリーに保つ**: 同じ目的へ向かう issue 群だけを1本の依存チェーンにまとめる。無関係な作業を同じチェーンに混ぜない(別スタックになる)
- **段を積みすぎない**: 下段がマージされるたび上段すべてが rebase される。チェーンが伸びるほど1回のマージで動く範囲が広がるため、独立して出せる塊があれば別チェーンに分ける

起票は依存順(blocker が先)に行う。実装側でスタックを積む手順は gh-stack スキルに従う。

### 例外: wide refactor は expand–contract で並べる

リネームや共有シンボルの再定義のように、**1つの機械的変更が全コードベースに波及する**もの(wide refactor)は、縦に切ろうとすると単体で green にできない。1つの振る舞いに押し込まず、次の順に並べる。

1. **expand**: 新しい形を旧い形の**隣に**追加する。この時点では何も壊れない
2. **migrate**: 呼び出し側を波及範囲ごと(パッケージ単位・ディレクトリ単位)のバッチで移す。各バッチを1 issue とし、expand を `Blocked by` に置く。旧い形が残っているのでバッチごとに CI は green を保てる
3. **contract**: 呼び出し側が無くなってから旧い形を削除する。全 migrate バッチを `Blocked by` に置く

バッチ単体でも green を保てない場合は、この順序のまま1本のスタックに積み、最上段に置いた「統合して検証する」issue へ全バッチを `Blocked by` として集約する。green を約束するのはその1件だけとする。

## フェーズ 5: タイトルとラベルを決める

- タイトルは日本語で簡潔かつ具体的にする
- 過去issueのラベル運用と既存ラベルの description を確認する
- カテゴリに対応する既存ラベルを優先する
- 適切な既存ラベルがない場合だけ、インタビュー中に新規ラベルを提案する
- ユーザーの承認なしに `gh label create` を実行しない
- `takt:*` などの workflow・自動化トリガー用ラベルは付与しない。過去 issue でその運用が見えても従わない（着手方式の判断は起票後に行う）

確定タイトルで既存 issue と再度照合する。インタビュー中にスコープが変わっている場合があるため、冒頭の重複確認とは別に最終ガードとして行う。類似 issue があれば新規作成前にユーザーへ確認する。

## フェーズ 6: プレビューして作成する

合意したリポジトリ、カテゴリ、タイトル、品質ゲート、ラベルと本文をプレビューする。インタビューでの合意を作成承認とみなし、類似issueがない限り追加確認なしで作成する。`--dry-run` はここまでで止める。

本文はテーブルとバッククォートを多く含むため、**`--body` に直接渡さず `--body-file` を使う**(下記「落とし穴」)。

```bash
cat > /tmp/issue-body.md <<'BODY'
## 概要
...
BODY

gh issue create --title "タイトル" --body-file /tmp/issue-body.md --label "label1,label2"
```

`--parent <N>` が指定された場合は、作成後に GraphQL で親へ接続する。

```bash
PARENT_ID=$(gh api repos/$OWNER/$REPO/issues/<親番号> --jq '.node_id')
CHILD_ID=$(gh api repos/$OWNER/$REPO/issues/<作成した番号> --jq '.node_id')
gh api graphql -f query="mutation {
  addSubIssue(input: { issueId: \"$PARENT_ID\", subIssueId: \"$CHILD_ID\" }) {
    issue { number } subIssue { number }
  }
}"
```

修正依頼があれば `gh issue edit --body-file` で追従する。

## 完了報告

報告するもの:

1. 作成した issue の URL とタイトル(分割した場合は**依存順に下段から**全件)
2. カテゴリと付与したラベル
3. 張った `blockedBy` 依存(= スタックの積み順)。`--parent` を使ったなら親への接続
4. 重複確認で見つかった類似 issue と、それでも新規作成した理由(あれば)
5. `--no-split` で押し込んだ場合は、混ざっている振る舞い
6. 品質ゲートを特定できず本文に「未確定」と書いた項目(あれば)

本文の内容は会話に再掲しない。**次に takt へ積むか自分で実装するかは提案しない**(着手方式の判断は起票の外)。

## 落とし穴

- **`--body` に本文を直接渡すとシェルが展開する**。本文には `` `src/file.ts` `` の
  バッククォートと `$` を含むテーブルが並ぶため、コマンド置換が走って本文が壊れるか、
  最悪シェルコマンドとして実行される。**quoted heredoc (`<<'BODY'`) でファイルに書き、
  `--body-file` で渡す**。`gh issue edit` も同様
- **存在しないラベルを `--label` に渡すと issue ごと作成に失敗する**。`gh` はラベルを
  自動作成せずエラーで止まるので、フェーズ 1 の `gh label list` と必ず照合する。
  綴りの揺れ(`enhancement` / `feature`)も実在名に合わせる
- **`gh issue list --limit 30` は直近分しか見えない**。重複確認は
  `gh search issues` のキーワード検索を必ず併用する(list だけで「無い」と判断しない)
- **`addBlockedBy` は blocker が既に存在していないと張れない**。node ID を要求するため、
  分割時の作成順は依存順(blocker が先)に固定される。上段から作ると張り直しになる
- **依存を本文にも書くと正が2箇所に割れる**。ネイティブの blocking 関係だけを正とする。
  本文の `Blocked by` は必ず古くなる
- **`blockedBy` は order.md に伝播しない**。takt に積むと本文だけが order.md へコピーされるため、
  依存を GitHub 側にだけ持たせると**段の位置づけが実装者に届かない**。依存そのものは
  `addBlockedBy` を正としたまま、**段番号と積み増し先 PR だけ**を本文の `位置づけ` に書く
- **issue 本文は takt に積んだ時点で order.md へコピーされる**。積んだ後に本文を直しても
  実行中・実行済みのタスクには反映されない。**本文の品質がそのまま実装の入力になる**ので、
  起票時に確定させる(積み直しが要るときは takt スキルの責務)
- **`.github/ISSUE_TEMPLATE/` があるリポジトリではテンプレートの構成が優先**。
  この出力契約で上書きせず、テンプレートに無い項目(要件・完了契約・スコープ外)だけ補う

## Rules

- APIキー、トークン、パスワード、接続文字列、個人情報を `***REDACTED***` に置換する
- `参照資料` と `影響ファイル` は可能な限り実在する相対パスで書き、位置は `` `file:line` `` 形式にする
- `要件` `完了契約` `スコープ外` は空のまま作成しない
- 完了契約の「拒否すべき誤実装」を空にしない。もっともらしい反例を挙げられない契約は、要件がまだ観測可能になっていない
- 契約ID は内容を表す slug にする。連番・行番号を ID にしない
- 1 issue に振る舞いを2つ以上含めない。「何が1つ変わるか」を1文で言い切れない起票を作らない
- 依存関係は GitHub ネイティブの `addBlockedBy` で登録し、本文に `Blocked by` を書いて代用しない(正が2箇所に分かれるため)
- 品質ゲートを特定できない場合はコマンドを捏造せず、その旨を記載する
- 本文に実行手順・判断基準の詳細・着手方式のルーティングを書かない(出力契約の責務外)
- 本文は日本語で書き、コード・識別子・技術用語は原表記を保つ
- 新規 issue 作成以外の GitHub 操作へ範囲を広げない。既存 issue の編集・クローズ・ラベル整理には踏み込まない
