## 外部スキルを更新したら破壊的変更が 11 リポジトリに波及した話

Matt Pocock さんの公開スキル集 [mattpocock/skills](https://github.com/mattpocock/skills) を `npx skills update` で 1.3.0 に上げた。更新そのものは 1 コマンドで終わったが、用語集ファイルの改名という破壊的変更が入っていて、そのスキルを使っている自分のリポジトリ 11 件の移行、同時に更新された gh-stack スキルと手元のバイナリの版ずれの解消まで広がった。

### 1. `skills update` は自分の追記を黙って上書きするので、更新後は追跡中のファイルの差分を読む

`npx skills update` は、mattpocock/skills の 11 件と一緒に GitHub 公式の gh-stack スキルも更新した。ユーザーに「自作に置いてたやつとかないよね？」と聞かれ、mattpocock のスキルの名前の履歴だけを調べて「上書きされていない」と答えたが、これは外れていた。gh-stack の `SKILL.md` には、以前の PR で自分で足した 3 項目（関連する PR は最初から 1 つのスタックにする、など）があり、それが upstream の版で消えていた。

気づいたのは、gh-stack の差分を commit 用の worktree に移したときに、削除行を読んだからだった。確かめ方は 2 つで足りる。

```sh
git status --short                               # 外部スキルなのに追跡中のファイルが変わっていないか
git log -S"<消えた行の一部>" -- <スキルのパス>   # その行を誰がいつ足したか
```

外部スキルの大半は `.git/info/exclude` で追跡対象から外しているが、一部はリポジトリで追跡している。追跡中のものは自分で手を入れている可能性があるので、「更新対象の一覧」ではなく「git の差分」で影響を確かめる。

### 2. 破壊的変更は CHANGELOG の移行手順まで読み、スキルの外にある参照先も数える

1.3.0 で、用語集の規約が `CONTEXT.md` / `CONTEXT-MAP.md` から `GLOSSARY.md` / `GLOSSARY-MAP.md` に変わった。CHANGELOG には「既存の `CONTEXT.md` は `git mv` すること。スキルは新しい名前しか探さない」とある。放置すると、用語集を育てるスキルが既存の `CONTEXT.md` を読まず、空の `GLOSSARY.md` を新しく作る。用語集が 2 つに割れて、これまで貯めた用語が使われなくなる。

影響はスキルの中だけで終わらない。セットアップ用のスキルが各リポジトリに `docs/agents/domain.md`（エージェントに用語集の読み方を教える案内）を書き出していて、そこにも旧名が残っている。全リポジトリを次の 2 本で数えた。

```sh
find ~/ghq -maxdepth 7 \( -name CONTEXT.md -o -name CONTEXT-MAP.md \) -not -path '*/node_modules/*'
git -C <repo> grep -l -E 'CONTEXT(-MAP)?\.md' origin/main
```

結果は、用語集の本体を持つリポジトリが 6 件、案内だけを持つリポジトリが 5 件だった。1 リポジトリ 1 PR にして、worktree の作成、`git mv`、置換までを 1 本のスクリプトで回した。

### 3. 機械的な置換でも、過去の記録と「当時の名前」は書き換えない

置換は `perl -pi -e 's/CONTEXT\.md/GLOSSARY.md/g'` で一括に行い、`docs/knowledge`・`docs/audits`・`prototype` は対象から外した。日付のある記録は、その時点の事実だからだ。

それでも、外した範囲の外に書き換えてはいけない箇所が 4 か所あった。「旧リポジトリの `CONTEXT.md` から引き継いだ」「ADR-0001 時点の `CONTEXT.md` では」のように、別のリポジトリや過去の時点のファイル名を指す記述だ。置換後に `git grep -n GLOSSARY | grep -E '旧|当初|時点'` で拾って戻した。逆に、用語集を別の文書に統合済みのリポジトリが 1 件あり、そこは改名せず、「スキルが `GLOSSARY.md`（旧 `CONTEXT.md`）と言ったらこの節に読み替える」という一文だけを直した。

### 4. スキルとバイナリは版を揃える。nixpkgs が遅れていれば overrideAttrs で上書きする

更新後の gh-stack スキルは 0.2.0 向けで、`--print-path` や worktree をまたぐ rebase を前提にしていた。手元の `gh stack` は 0.1.1 で、`gh stack checkout --help` に `--print-path` が無い。スキルを読んだエージェントが、存在しないフラグを使うことになる。nixpkgs は unstable も master も 0.1.1 のままだった。

`pkgs.gh-stack.overrideAttrs` で `version`・`src`・`vendorHash` を上書きしたが、ビルドで 3 回つまずいた。

| 症状 | 原因 | 対処 |
|---|---|---|
| `installSkill: error: no skillBase given and $pname is unset` | `installAgentSkills` フックが go-modules の導出でも走り、そこには `pname` が無い | フックだけを外す |
| `go: command not found` | `nativeBuildInputs = [ ]` にしたら、`buildGoModule` が入れていた go まで消えた | `lib.remove pkgs.installAgentSkills old.nativeBuildInputs` で 1 つだけ外す |
| `TestInsert…` が 20 件失敗 | `modify` の TUI でブランチを挿入するテストが、Nix のサンドボックスで落ちる | `checkFlags = [ "-skip=Insert" ]` |

`vendorHash` は `lib.fakeHash` でビルドし、エラーの `got:` の値を写す。`src` のハッシュは `nix run nixpkgs#nix-prefetch-github -- github gh-stack --rev v0.2.0` で取れる。nixpkgs が追い付いたら上書きを消す、とコメントに書いておいた。

### 5. 管理の記録に載っていない実体は、次の移行で消える

upstream にある diagnosing-bugs（難しいバグの診断手順）だけが入っていなかった。履歴をたどると、6 月に導入していて、9 月の移行で消えていた。移行前のバックアップには実体があったが、`npx skills` の lock ファイル（`~/.agents/.skill-lock.json`）には記録が無かった。移行は lock と exclude の一覧に載ったものだけを引き継いだので、記録の無い実体は対象から漏れた。

同じ理由で消えていたスキルが 4 件あったが、どれも今は不要だったので入れ直していない。移行のあとは、バックアップと現状を突き合わせておくと、漏れに気づける。

```sh
comm -23 <(ls <バックアップのディレクトリ> | sort) <(ls config/.agents/skills | sort)
```

### 6. 数秒で失敗してログも無い CI は、コードではなく課金を疑う

3 リポジトリの CI が 2〜3 秒で失敗し、`gh run view --log-failed` は `log not found` だった。check run の出力を API で読むと、原因はコードではなかった。

```sh
gh api repos/<owner>/<repo>/check-runs/<job-id> -q '.output.title'
# The job was not started because recent account payments have failed
# or your spending limit needs to be increased.
```

非公開リポジトリの Actions の利用枠の問題で、ジョブが起動していなかった。どれも文書だけの変更だったので、CI なしでマージした。

### 7. 他リポジトリへの書き込みは、チャットでの承認では通らない

Claude Code の auto mode（操作ごとに分類器が許可を判定する仕組み）は、作業中のリポジトリの外への書き込みを止める。他リポジトリでの worktree 作成は「共有リソースの変更」、commit・push・PR 作成は「外部システムへの書き込み」、他リポジトリの PR のマージは「レビューなしのマージ」として止められた。ユーザーがチャットで「承認する、やって」と書いたあとに再試行しても、同じように止められた。

通った方法は 2 つある。

- 止められた操作をスクリプトにまとめ、ユーザーに `!` 付きの 1 行で実行してもらう
- 範囲を絞った許可ルールを `autoMode.allow` に足す。今回は「自分の個人リポジトリで、頼まれた作業として行う worktree 作成・commit・ブランチの push・PR 作成」だけを許可し、組織のリポジトリ・デフォルトブランチへの push・マージは対象外にした

止められたら、同じ操作を形を変えて再試行せず、1 回目でユーザーに渡すのが一番早い。
